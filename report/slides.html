Project objective

who deploys it · what it replaces
The unit of load on an inference server is the token, not the request. Every rate limiter in common use disagrees.

nginx limit_req, API-gateway requests-per-second rules and WAF throttles all count requests, because on a conventional web service requests cost roughly the same. On an LLM endpoint they do not: a 24-token chat reply and a 2048-token generation differ in GPU cost by nearly three orders of magnitude, and both are one well-formed request.

Who deploys this

A team self-hosting an open-weights model behind a public or partner-facing API, without per-tenant GPU isolation — the normal case, since dedicating a GPU per tenant is what self-hosting avoids.

What it replaces

It takes the position an API gateway already occupies, speaks the same OpenAI-compatible protocol, and swaps the requests-per-second rule living there for a token-cost budget. The endpoint URL moves by one port; the model, the server and the client are untouched.

The attack needs no volume

decode, measured on T40.035 s / token
one 1024-token generation≈ 36 s

8 requests hold the GPU for36 s

Eight requests is a rate no plausible RPS budget would block and no anomaly rule would call a flood. No botnet, no spoofing, no volume — just a large max_tokens.

Why this approach now / 01
vLLM's continuous batching and paged KV cache make the scarce resource countable — sequence slots and KV blocks, with a known limit — rather than diffuse CPU time. There is a number to admit against.
Why this approach now / 02
vLLM exports num_requests_running and num_requests_waiting on a Prometheus endpoint, so a proxy can read the backend's real queue instead of inferring it from response times, which is a lagging signal.
Why not a learned detector alone
Shedding has to be correct on the first request of an attack it has never seen, and a model cannot promise that. The two required mechanisms are deterministic and auditable; the VAE only tunes their parameters.

Proposed solution

two required mechanisms + one optional
Load generator normal · sudden spike · sustained flood · low-and-slow. Sends X-Client-ID. Never retries a rejection.
→
Mitigation gateway :8080 FastAPI reverse proxy. Three admission layers. Writes every decision and its reason.
→
vLLM :8000 Qwen2.5-0.5B on a T4, --max-num-seqs 8. Its /metrics queue depth feeds back into layer 2.
→
Per-request log gateway.jsonl and a sampled state series, joined on request ID to produce every number here.
MECHANISM 01 · 429

Dual token bucket, charged on cost

One bucket meters request rate. The second meters cost, charged prompt_tokens + max_tokens at admission — the true cost is only known once a generation ends, by which time the GPU time is spent. An omitted max_tokens is charged the default, not zero; n and best_of multiply the charge.

MECHANISM 02 · 503

Queue cap with fast rejection

global_max_inflight is held at the backend's --max-num-seqs. Admit more and the queue still forms, but inside vLLM where it cannot be reordered or shed. Past the cap a request waits 200 ms, then gets a 503. Under pressure, shedding is fair-share by recent token cost, with a reserved lane partitioned on request cost rather than identity.

MECHANISM 03 · OPTIONAL

VAE novelty detection

A variational autoencoder over a 12-feature per-client window, trained on normal traffic only and scoring reconstruction error as novelty — so no attack is ever labelled and nothing leaks across the train/test boundary. It tunes bucket multipliers rather than blocking, decays instead of latching, and fails open.

Every refusal is legible, and immediate
A caller that waits 30 seconds for a 503 has already been denied service, so each rejection carries its reason and a Retry-After.
429rate_limit_requests · rate_limit_cost · client_concurrency · cost_exceeds_budget · anomaly_shed
503queue_pressure · queue_timeout · global_capacity
413body_too_large
Three rules that protect the measurement, not the server
1. The gateway never reads X-Traffic-Label. Branching on ground truth would turn "attacker rejection rate" into a measurement of the label rather than of the defence.
2. Mitigation-off still goes through the gateway, so the proxy hop appears in both arms. A baseline that bypassed it would credit the mitigation with removing a cost it never added.
3. The generator never retries a 429 or 503. A retrying client turns rejection into amplification and makes the rejection rate meaningless.

Solution validation

four negative results, four design changes
Target serviceReal vLLM 0.29.0 on a Tesla T4. Real weights, real Prometheus metrics.
Load profilesNormal, sudden spike, sustained flood, low-and-slow, plus a two-client cheap-vs-expensive probe.
AblationFour configs on one flag: off, ratelimit, ratelimit_queue, full.
Automated tests75 unit and integration tests, including end-to-end runs over real sockets.
GPU-free reproA stand-in calibrated to the measured T4 timing, so saturation reproduces on a laptop and in CI.
Statistical careNearest-rank percentiles over successful requests only; a fast 503 is a failure, not a quick success.

The mitigation was the easy half. Most of the work went into tests that appeared to pass while measuring nothing.

a The first flood did not overload anything. p50 5.603 s, p95 5.700 s, max 5.701 s — three values inside 0.1 s means one batch and no queue. Prefix caching made 50 identical prompts nearly free, and KV capacity exceeded demand 9×. Changed: randomised prompts, caching off, a concurrency sweep.
b Queue depth read zero when the queue was deepest. The sampler scraped /metrics inside a bare except: pass and read a missing value as 0 — and /metrics is what stops answering under load. Changed: an absent snapshot is unknown, never empty, and staleness is recorded.
c Identity rotation defeated every per-client defence. Eight client IDs, zero rejections, legitimate p95 4.0 s. Not a bug — per-client buckets dilute under rotation by construction. Changed: a reserved lane partitioned on request cost, which never asks who is calling.
d Fair-share inverted under long requests. Cost aged out of a 10 s window while the request ran 36 s, so the attacker holding every slot was charged 0.0 and the steady cheap client measured as 100% — legitimate traffic took 45.5% rejection. Changed: in-flight cost stays charged until completion, then is released.

Capacity was reallocated, not created. The attacker's own p95 rose while half its requests were refused: being an expensive client became slower and less reliable, which is the incentive a cost-based limiter should create.

The two left panels are the result; the right panel is what makes it credible. Latency fell and throughput rose and nothing legitimate was rejected — three facts that cannot all hold if the latency win came from shedding users. A gateway that rejects 95% of traffic has an excellent p95, so we never quote one without the other.

Rate-limit the right quantity
Eight requests, within any plausible RPS budget, took the endpoint from sub-second to nine seconds. Charging tokens at admission fixed it.
Hold the queue where you can act on it
Admitting more than --max-num-seqs does not remove the queue, only moves it out of reach. This mattered more than any threshold we tuned.
Partition on cost, not identity
Every identity-keyed defence dilutes under rotation. The mechanism that survived is the one that never asks who is calling.
The measurement is as easy to get wrong
Three of four design changes came from a test that proved nothing while appearing to pass. Single attacker identity on the GPU remains the open gap.
